# v2.0.0 基础架构重建设计

- **状态：** 设计与工程评审均已批准，可进入实施计划
- **日期：** 2026-08-03
- **目标版本：** v2.0.0
- **前置版本：** v1.3.0

## 1. 背景与结论

v1.3.0 已完成 Service Worker 行情中心化、Popup RPC 化、schema v2、真实行情降级、串行写入、自动化测试和确定性发布。但当前工程仍存在影响长期维护和稳定性的结构问题：

1. Popup 只是按 `State / Render / Actions` 横向拆分，尚未形成自治组件；`popup-render.js` 与 `popup-actions.js` 合计超过 1300 行，并通过全局对象双向耦合。
2. Popup 共享状态可被直接修改，业务命令、DOM 更新、事件绑定和异步副作用没有统一的数据流。
3. 运行时同时使用经典脚本、全局变量和 CommonJS 测试出口，模块依赖依靠 HTML 与 `importScripts()` 加载顺序维持。
4. RPC 以字符串 action 和分散校验组成，缺少版本、共享类型、请求关联和统一错误模型。
5. `storage.js` 同时承担迁移、用户数据、缓存和并发控制，边界过宽。
6. Popup 最大的两个模块未进入 TypeScript 和 c8 覆盖率门禁；现有无障碍测试覆盖不足，文档声明与实际实现存在偏差。

v2.0.0 将一次性重建底层架构，而不是增加新的业务功能。目标是建立统一的 TypeScript/ESM 运行时、可验证的分层依赖、单向状态流、组件契约、存储仓储、版本化 RPC、结构化诊断和完整质量门禁。

## 2. 目标与非目标

### 2.1 目标

- 所有运行时 JavaScript 改为 TypeScript 源码，经 `tsc` 输出原生 ES Modules。
- 保持零运行时第三方依赖，不引入前端框架或打包器。
- Popup 使用 Light DOM Web Components，形成可独立理解、测试和替换的组件。
- Popup 使用不可变 Store、纯 Reducer、Selector 和 Command 构成单向数据流。
- Service Worker 成为存储、行情和搜索等远端数据访问的唯一所有者。
- RPC 使用共享类型、运行时校验、协议版本、请求 ID 和结构化错误。
- 将存储迁移、用户数据和行情缓存拆成独立职责，并由唯一 `StorageCoordinator` 统一一致性读写与串行临界区，同时保持 schema v2 数据兼容。
- 运行正确性不依赖 Service Worker 内存状态。
- 建立 TypeScript、架构约束、单元、组件、E2E、axe、覆盖率和确定性打包门禁。
- 补齐完整键盘操作等价、焦点管理、ARIA、触控目标和 WCAG 2.1 AA 对比度。

### 2.2 非目标

- 不实现价格阈值提醒、Chrome 通知、提醒历史或静默时段。
- 不改变行情数据源和真实行情优先、缓存降级、禁止模拟价格的业务语义。
- 不新增 Chrome permissions 或 host permissions。
- 不引入 React、Preact、Lit、运行时状态库或运行时校验库。
- 不改变 schema v2 的持久化语义，不执行破坏性迁移。
- 不同时发布或运行新旧两套 Popup。

## 3. 架构原则

依赖只能由外向内：

```text
Presentation (Popup Components)
        ↓
Application (Commands / Services / Ports)
        ↓
Domain (Models / Rules / Errors)

Infrastructure (Chrome / Storage / HTTP)
        ↓ implements
Application Ports
```

具体约束：

- Domain 不得依赖 `chrome`、DOM、`fetch`、系统时间或 Infrastructure。
- Application 只能通过 Ports 使用持久化、网络、时钟和诊断能力。
- Infrastructure 实现 Ports，不得反向调用 Presentation。
- Popup 组件不得导入 Bridge、Repository、HTTP Provider 或其他组件实例。
- Background 和 Popup 各有一个 Composition Root，负责创建依赖和生命周期注册。
- 共享类型和协议不得引用 DOM 或 Chrome API 类型。
- 架构检查脚本必须拒绝反向 import 和跨层循环依赖。

构建规则：

- TypeScript 使用 `strict: true`、`module: ES2022`、`target: ES2022`、`moduleResolution: Bundler`。
- 使用 Project References 分离编译环境：Domain/Protocol 只允许 `ES2022`，Popup 允许 `DOM`，Background/Chrome Infrastructure 允许 `WebWorker` 与 Chrome 类型；共享层不得看到 DOM 或 Chrome 全局类型。
- 源码中的本地模块 import 必须显式使用 `.js` 后缀，保证 `tsc` 原样输出后可被浏览器 ESM 解析。
- Runtime 源码禁止 bare import、路径别名和省略扩展名的相对 import；构建后脚本必须逐个解析 emitted import target，缺失目标立即失败。
- TypeScript 使用 `noEmitOnError: true`、`sourceMap: false`，发布目录不产生声明文件或 Source Map。
- `src/` 编译到 `build/extension/runtime/`，目录结构保持不变。
- 构建脚本先清理专用构建目录，再复制 `extension/` 静态文件并运行 `tsc`。
- `manifest.json` 注册 `runtime/background/main.js`，并设置 `background.type = "module"`。
- `popup.html` 只加载 `runtime/popup/main.js`，使用 `<script type="module">`。
- Chrome 开发者模式和 Playwright 均加载 `build/extension/`，不直接加载源码根目录。
- 从第一个构建提交起，`build/extension/` 必须始终是可由 Chrome/Playwright 加载的非发布 v2 集成壳；实现期间不引入生产双协议或旧运行时适配层。
- `build/` 与 `dist/` 不提交 Git；发布包只从干净构建生成。

## 5. Domain 与 Application

Domain 包含稳定的值对象、实体和纯规则：

- `StockCode` 规范化与市场判定。
- `Group`、`Stock`、`BoardConfig` 和 `Quote` 类型。
- `g_all` 计算视图语义。
- 排序、筛选、置顶和手动顺序规则。
- 行情 `fresh / cached / missing` 状态与可用价格判定。
- 稳定错误码与领域校验错误。

Application 以用例组织，而不是以页面或 Chrome API 组织：

- Quotes：缓存读取、双源刷新、分批、超时、退避和快照生成。
- Portfolio：分组与股票增删改、移动、置顶和排序。
- Preferences：看板配置读取和补丁持久化。
- Search：远端搜索、本地热门数据降级和结果规范化。

Application Ports 包含：

- `UserDataRepository`
- `QuoteCacheRepository`
- `QuoteProvider`
- `StockSearchProvider`
- `Clock`
- `DiagnosticSink`
- `AlarmPort`
- `ActionPresenterPort`
- `SessionStatePort`

时间、网络、Chrome Storage 和 Console 均由 Infrastructure 注入。单元测试使用内存实现和确定性时钟。

抽象准入规则：

- 只为真实外部副作用建立 Port；不得创建 `BaseRepository`、`BaseService`、`BaseComponent` 或只有一个转发方法的包装层。
- Web Component 只用于确实需要生命周期、焦点管理或稳定节点身份的 UI 单元；纯格式化和纯 ViewModel 映射保持普通函数。
- RPC 方法、payload、result 和 validator 必须由同一穷尽式 typed registry 导出，不维护平行字符串清单。

## 6. RPC v2

### 6.1 方法集合

```text
app:bootstrap
quote:refresh
stock:search
stock:add
stock:remove
stock:move
stock:setPinned
stock:setOrder
group:create
group:rename
group:delete
group:setOrder
preferences:patch
```

`app:bootstrap` 一次返回用户数据、全部看板配置和缓存行情，替代 v1.3.0 启动阶段的多次读取。搜索迁入 Service Worker，Popup 不再直接加载行情传输模块。

### 6.2 消息格式

```ts
type RpcRequest<M extends RpcMethod> = {
  protocol: 2;
  requestId: string;
  method: M;
  payload: RpcPayloadMap[M];
};

type RpcResponse<T> =
  | { protocol: 2; requestId: string; ok: true; data: T }
  | {
      protocol: 2;
      requestId: string;
      ok: false;
      error: {
        code: ErrorCode;
        message: string;
        retryable: boolean;
      };
    };

type MutationMeta = {
  expectedRevision: UserDataRevision;
};

type MutationResult<T> = {
  value: T;
  userData: UserData;
  revision: UserDataRevision;
};
```

约束：

- Popup Client 和 Background Router 从同一 `RpcPayloadMap` 与 `RpcResultMap` 获取类型。
- Router 对每个方法执行无第三方依赖的运行时 payload 校验。
- 所有写方法表达最终期望状态并携带 `expectedRevision`；分组 ID 由 Popup 在发命令前生成，禁止 toggle、服务端随机 ID 和非幂等相对修改。
- `stock:setPinned` 在一个事务中同时写入最终 pinned 状态与相关 manual order；`stock:setOrder` 在一个事务中同时写入 manual order 与 `sortField = 'manual'`。
- 未知方法返回 `UNKNOWN_METHOD`，协议不匹配返回 `PROTOCOL_MISMATCH`。
- `requestId` 贯穿 Router、Application、Repository 和诊断日志。
- RPC Client 统一处理 `chrome.runtime.lastError`、空响应、超时和结构化错误。
- Router 使用 `sendResponse()` 并字面量 `return true` 保持消息通道；每个请求只能响应一次，并以自动化测试覆盖同步异常、异步成功和异步失败。
- 写请求超时进入 `uncertain`，Popup 重新调用 `app:bootstrap` 并以命令的 desired-state predicate 判断是否已经提交；未提交才允许用新 revision 安全重试，不执行盲目回滚。
- 搜索和行情用 requestId/generation 拒绝过期响应。
- v2.0.0 原子发布 Popup 与 Background，不长期维护 v1/v2 双协议。

## 7. Storage 架构与数据兼容

```text
ChromeStorageAdapter
└── StorageCoordinator（唯一读写队列与临界区）
    ├── UserDataRepository
    │   ├── groups
    │   ├── watchlist
    │   └── boardConfig
    ├── QuoteCacheRepository
    │   └── quoteCache:<code>
    └── MigrationService
        ├── v0 → v1
        └── v1 → v2
```

### 7.0 StorageCoordinator

- `StorageCoordinator` 是 `chrome.storage.local` 的唯一业务调用者和唯一写入队列；Repository 不得持有独立队列或绕过 Coordinator 调用 Adapter。
- 用户数据、缓存写入、缓存删除和一致性读取均进入同一临界区，防止用户删除与迟到缓存写入产生竞态。
- `app:bootstrap` 在只读临界区内完成用户数据读取/清洗、revision 计算、股票代码集合冻结和对应 quote cache 批量读取；临界区内禁止网络请求。
- `userDataRevision` 是规范化 `groups + watchlist + boardConfig` 内容的 SHA-256 摘要，不作为独立 Storage key 持久化；v1.3.0 回滚写入后，下一次 v2 bootstrap 会自然得到新的 revision。
- 写命令先对最新内容计算 revision；不匹配 `expectedRevision` 时返回 `CONFLICT` 和最新 bootstrap 所需数据，不执行任何写入。

### 7.1 UserDataRepository

- 读取后统一执行 schema v2 清洗并返回领域对象副本。
- 所有用户数据修改经过同一串行 Unit of Work。
- `g_all` 保持计算视图，不写入 `groupIds`。
- 分组、股票和 BoardConfig 修改必须保留无关字段。
- 写入失败不得向调用方返回成功状态。

### 7.2 QuoteCacheRepository

- 缓存继续使用独立的 `quoteCache:<code>` 键。
- 只接受 `price > 0` 的有效行情。
- 损坏或超过七天的条目删除并标记 missing。
- 缓存写入前重新检查股票是否仍在 watchlist，防止迟到写入复活孤儿缓存。
- 缓存异常发出结构化事件并重新抛出原始错误。
- 初始化时清理 watchlist 之外的孤儿缓存，恢复 Service Worker 在多键写入中途终止可能留下的可恢复残留。

### 7.3 MigrationService

- 继续使用 schema v2，不创建无业务必要的 schema v3。
- 保留 `migrationBackup:v1.2.1`，备份不可被重复迁移覆盖。
- v0、v1、v2 迁移必须幂等。
- v2.0 不保留 v1 RPC、旧运行时模块或双轨架构；只保持 schema v2 用户数据可由冻结的 v1.3.0 发布包安全读取，以支持运维回滚。
- v2.0.0 不向 `groups`、`watchlist` 或 `boardConfig` 写入 v1.3.0 无法理解的新必需字段；新增 UI 异步态和 Overlay 状态只存在于 Popup 内存。
- 历史版本真实数据快照进入固定兼容测试夹具。
- 反向兼容测试使用冻结的 v1.3.0 清洗/读取实现回读 v2.0 数据，不能用 v2.0 自身解析器代替。

## 8. Service Worker

`background/main.ts` 仅负责组合和注册：

```text
创建 ChromeStorageAdapter
→ 创建 Repository 与 Application Services
→ 创建 Quote/Search Providers
→ 注册 Router
→ 注册 Alarm、Installed、Startup、Storage listeners
→ 等待事件
```

生命周期要求：

- 所有 Chrome listener 在模块顶层同步注册，不等待任何异步初始化；handler 进入后统一等待共享、可重试的初始化屏障。
- 初始化屏障只有 `idle / running / ready` 三态；初始化失败必须从 `running` 回到 `idle`，让下一事件重试迁移、备份、孤儿缓存清理、session 退避读取与 alarm 校验。
- 注册幂等，不重复添加 listener。
- Service Worker 可在任意事件后被销毁并无损重建。
- 正确性只依赖持久化数据；退避状态写入 `chrome.storage.session`，single-flight 和当前 runId 可以随实例丢失。
- 空自选股不请求网络，也不改变退避状态。
- 每次 Service Worker 激活都执行 `ensureAlarm`，不得假定 alarm 一定跨浏览器重启存在。
- 每次行情任务开始前先创建最迟安全 Alarm，任务结束后再替换为按市场状态计算的精确一次性 Alarm；Provider 或缓存异常不得造成永久停止调度。
- Background 自己调用 Application Services，不绕过 Repository 或复制业务规则。
- Badge 和 Tooltip 由独立 Presenter 根据 QuoteSnapshot 生成。

## 9. Popup 单向状态架构

### 9.1 AppState

```ts
interface AppState {
  domain: {
    groups: Group[];
    watchlist: Stock[];
    boardConfig: Record<GroupId, BoardConfig>;
    quotes: QuoteSnapshot;
  };
  view: {
    currentGroupId: GroupId;
    searchKeyword: string;
    selectedCodes: StockCode[];
  };
  async: {
    bootstrap: AsyncState;
    quoteRefresh: AsyncState;
    stockSearch: AsyncState;
    mutations: Record<string, AsyncState>;
  };
  overlay: {
    dialog: DialogState | null;
    menu: MenuState | null;
    toast: ToastState | null;
    focusReturnId: string | null;
  };
}
```

状态约束：

- Reducer 是唯一状态写入口，所有转换均为纯函数。
- State 不保存 DOM、组件实例、Promise、Timer 或可变 `Set`。
- `domain.boardConfig` 是 viewMode、sort、columns 和 priceHidden 等持久偏好的唯一真相；`view` 只保存当前分组、搜索、选择和其他会话态。
- Selector 从 `domain.boardConfig[currentGroupId]` 派生当前视图偏好，并负责分组过滤、排序、列选择和 ViewModel 生成。
- Command 负责 RPC、副作用、并发锁和 requestId，并把结果转换为 Action。
- 持久化命令以服务端返回的 authoritative `MutationResult` 更新 Store；超时进入 uncertain 并执行 bootstrap 对账，禁止把未知提交状态当作失败回滚。
- 删除、移动等破坏性操作在后台确认或对账确认后才更新 Store。

### 9.2 组件树

```text
<stock-app>
├── <stock-header>
├── <group-tabs>
├── <stock-toolbar>
├── <stock-board>
│   ├── <stock-grid> → <stock-card>
│   └── <stock-table>
├── <quote-status>
├── <batch-toolbar>
├── <column-panel>
├── <app-dialog-host>
└── <app-live-region>
```

`<stock-app>` 是 Popup Composition Root：订阅一次 Store，使用 Selector 生成 ViewModel，向子组件赋值，并把语义事件路由到 Command。子组件不得导入 Store、Bridge、Repository 或其他组件实例。

### 9.3 组件事件

组件使用带类型、冒泡的 `CustomEvent`：

```text
group-select
group-reorder-request
stock-pin-request
stock-remove-request
stock-reorder-request
batch-move-request
view-mode-change
preferences-change
dialog-submit
quote-refresh-request
```

拖拽、鼠标菜单、触控和键盘操作必须触发同一个语义事件，不允许复制业务逻辑。

### 9.4 渲染规则

- 组件首次连接时创建稳定 DOM，后续只更新属性、文本和必要节点。
- 股票与分组列表按稳定 ID keyed update，不整树替换 `innerHTML`。
- 动态用户或 Provider 内容只能通过 `textContent` 或安全属性写入。
- `connectedCallback()` 使用每次连接新建的 `AbortController` 注册事件，`disconnectedCallback()` 统一 abort 并清理 Timer 和订阅；重复连接不得累积 listener。
- Light DOM 组件使用统一前缀类名和 CSS 分层，避免样式泄漏。

## 10. 无障碍设计

- 所有操作使用原生 `button`、`input`、`select`、`table` 和 `dialog`。
- 分组 tablist 支持方向键、Home、End、Enter 和 Space。
- 股票搜索实现 combobox/listbox 与 `aria-activedescendant`。
- 股票卡片使用 `article` 和独立操作按钮，不嵌套冲突的交互角色。
- 列表使用语义化 table，排序表头包含真实按钮和 `aria-sort`。
- Dialog 统一使用 `showModal()`、Escape、焦点陷阱和关闭后的焦点返回。
- 分组、股票和列排序均提供上移/下移按钮和键盘快捷方式。
- 排序、拖拽、刷新和错误恢复通过 live region 宣告。
- 所有主要触控目标至少为 44×44px。
- 颜色对比度以实际前景色和实际背景色组合计算，正常文本不低于 4.5:1。
- `prefers-reduced-motion` 下关闭非必要动画。
- Bootstrap 显示骨架屏；失败显示可恢复错误页和重新连接操作。

## 11. 错误处理

```ts
type ErrorCode =
  | 'UNKNOWN_METHOD'
  | 'INVALID_PAYLOAD'
  | 'PROTOCOL_MISMATCH'
  | 'STORAGE_UNAVAILABLE'
  | 'QUOTE_TIMEOUT'
  | 'QUOTE_UNAVAILABLE'
  | 'SEARCH_UNAVAILABLE'
  | 'CONFLICT'
  | 'NOT_FOUND'
  | 'VALIDATION_FAILED'
  | 'INTERNAL';
```

每个应用错误包含稳定错误码、安全用户文案和 `retryable` 标记。堆栈和原始 Provider 响应不通过 RPC 暴露。

恢复策略：

- 行情失败保留七天内缓存并明确标记 cached。
- 搜索失败降级到本地热门股票数据。
- 写入失败不显示伪成功；写入超时显示“正在确认”，bootstrap 对账后再确认成功或允许重试。
- Bootstrap 失败显示最小故障界面而非白屏。
- 协议不匹配提示重新打开扩展。
- Popup root orchestration 通过显式 `renderAppSafely()` 包裹 Store→ViewModel→Component 更新；静态 fallback 位于可能失败的组件树之外，渲染异常时隐藏 `<stock-app>` 并显示可重试故障界面，不宣称 Custom Element 具备框架式 Error Boundary。
- 全局 `error` 与 `unhandledrejection` 转换为结构化诊断。

## 12. 可观测性

```ts
interface DiagnosticEvent {
  timestamp: number;
  version: string;
  requestId?: string;
  runId?: string;
  scope: 'rpc' | 'storage' | 'quote' | 'search' | 'scheduler' | 'ui';
  type: string;
  outcome?: 'ok' | 'degraded' | 'failed';
  durationMs?: number;
  errorCode?: ErrorCode;
  counts?: Record<string, number>;
}
```

- `requestId` 关联 Popup、Router、Application 和 Repository。
- `runId` 关联 Alarm 触发、Provider、缓存、Badge 和恢复结果。
- 不记录股票名称、分组名称或完整请求 payload。
- 默认 DiagnosticSink 输出本地 Console。
- 保留 Sink 接口供未来接入监控，但 v2.0.0 不接入第三方服务。
- 关键任务使用 `startSpan()` 产生开始、边界和恰好一次结束事件；RPC 与后台行情链路分别由 requestId/runId 贯穿。

## 13. 测试策略

测试工具链固定为：

- Node 原生 test runner 继续作为测试运行器。
- `tsx` 仅作为开发依赖加载 TypeScript 测试源码，不参与扩展生产构建或发布产物生成。
- `happy-dom` 仅用于 Web Component 单元与生命周期测试。
- `@axe-core/playwright` 用于真实扩展页面无障碍扫描。
- `c8` 使用 `tsx` 测试运行时提供的 Source Map 统计 TypeScript 源码，并显式包含全部 `src/**/*.ts`；这与发布构建关闭 Source Map 相互独立。
- 架构检查脚本使用现有 TypeScript Compiler API 读取 import graph，不增加运行时依赖。

### 13.1 静态门禁

- TypeScript strict 类型检查。
- ESLint 覆盖源码和测试，禁止未处理 Promise。
- 架构检查拒绝循环依赖和跨层反向 import。
- Manifest 权限、入口、CSP 和 host permissions 白名单验证。
- Runtime 第三方依赖数量必须为 0。

### 13.2 单元测试

- Domain 规则和格式化。
- Reducer、Selector 和 Commands。
- RPC 类型映射、运行时校验和错误映射。
- MigrationService、UserDataRepository 和 QuoteCacheRepository。
- QuoteService、SearchService、Scheduler 和诊断事件。

### 13.3 组件测试

使用仅开发依赖的轻量 DOM 环境验证：

- ViewModel 到 DOM 的映射。
- 语义事件和 payload。
- ARIA、禁用、加载和错误状态。
- 生命周期清理和重复连接。
- keyed update 保留节点身份、焦点和滚动位置。
- Dialog 打开、关闭和焦点恢复。

### 13.4 真实扩展 E2E

- 保留 v1.3.0 的 16 个现有场景作为行为基线。
- 覆盖添加、删除、移动、分组、置顶、排序、批量和配置。
- 覆盖分组创建/重命名/删除/重排、股票重排、批量移动/删除以及列重排，不以现有 16 个场景代替这些缺失流程。
- 覆盖缓存、离线、双源失败、损坏缓存和 Service Worker 重启。
- 覆盖快速重复操作、过期响应和并发写入。
- 覆盖 `expectedRevision` 冲突、RPC uncertain 对账、安全重试、Router exactly-once response 和初始化失败后重试。
- 覆盖完整键盘操作等价和焦点恢复。
- axe-core 在空状态、网格、列表、Dialog 和错误状态下不得出现 critical/serious 问题。
- 验证 90%–150% 缩放、44px 目标和实际颜色对比度。
- 捕获 Popup page error、未处理 Promise 和后台异常诊断。

### 13.5 性能与容量验收

- 固定 20 个分组、500 只股票夹具；`app:bootstrap` 在本地 Chrome E2E 中 p95 不超过 250ms，Popup 首次可交互 p95 不超过 500ms。
- 500 只股票的缓存 ViewModel 派生与 keyed DOM 更新各自 p95 不超过 100ms；测试预热 5 次、测量 20 次并输出原始样本。
- 行情刷新总 deadline 为 8 秒，单次 Provider 请求上限 4 秒，50 只/批，批次并发上限 2；deadline 到达时返回已完成批次与七天内缓存，不等待剩余请求。
- 性能断言使用固定 Chrome 版本的 Playwright CI 项目串行执行，禁止只记录日志而不设失败门槛。

### 13.6 覆盖率

- 全部 `src/**`：lines/statements 90%，branches 85%，functions 90%。
- Domain、Protocol、Storage、Reducer：lines/statements/functions 95%，branches 90%。
- 所有 Popup 组件必须纳入门禁。

## 14. 一次性迁移与回退

迁移顺序：

```text
冻结 v1.3.0 行为基线
→ 建立历史数据与 E2E 特征测试
→ 建立可加载的 v2 TypeScript/ESM 集成壳
→ 重写 Domain、Protocol、Repository 与 Application
→ 重写 Background
→ 重写 Popup Store 与 Components
→ 完成功能等价和无障碍验收
→ 将正式 Manifest 与 Popup 入口提升为完整 v2 产物
→ 删除旧运行时代码
→ 完整发布验收
```

“一次性”表示只发布一个 v2.0.0，不表示一个不可审查的大提交。实现阶段按依赖顺序形成小提交，每个提交必须通过相关层的静态检查和测试。

回退保证：

- 不执行破坏性 schema 迁移。
- v1.3.0 标签、ZIP 和 SHA 长期保留。
- v2.0.0 写出的 schema v2 数据可被 v1.3.0 读取。
- v2.0.0 不持久化只有新版本才能解释的必需字段。
- v2.0.0 运行时不包含 v1 RPC、旧模块适配器或双协议分支；Popup 与 Background 只作为同一个 v2 包原子发布。
- 保存冻结的 v1.3.0 发布 ZIP、SHA 与标签，并演练 `v1.3 → v2 写入 → Chrome Web Store 回滚上一发布包 → 再升级 v2`；严重故障使用商店回滚能力发布旧运行时，不恢复或转换用户数据。
- 分批发布不能作为唯一保护措施，因为商店百分比发布可能受活跃用户规模限制。

## 15. 发布门禁

```text
clean install
→ typecheck / lint / architecture checks
→ unit / component / E2E / axe
→ npm audit
→ build twice and compare SHA
→ ZIP allowlist and size check
→ clean-profile install
→ v1.3 data in-place upgrade
→ store assets and release notes
```

- 构建两次必须产生字节一致的 ZIP。
- ZIP 只包含可运行扩展文件，不包含源码、测试、Source Map 或项目文档。
- Bundle 继续执行 200 KB 提醒和 500 KB 硬限制。
- CI 与 Release workflow 必须使用同一构建入口。
- 发布说明必须准确列出架构升级、兼容保证和已验证测试。

## 16. 验收标准

1. 所有运行时 JavaScript 源码均为 TypeScript，并输出原生 ESM。
2. Runtime 无第三方依赖，无框架和打包器。
3. 不存在 `State / Render / Actions` 全局单例或依赖脚本加载顺序的业务模块。
4. 架构检查不存在循环依赖和反向跨层 import。
5. Popup 组件只接收 ViewModel、发出语义事件，不访问 Bridge 或 Repository。
6. Reducer 是 AppState 的唯一写入口。
7. Popup 的远端行情和搜索请求全部经过 Service Worker。
8. RPC v2 类型、运行时校验、requestId、超时和结构化错误完整。
9. schema v2、迁移备份、`g_all`、内容 revision、唯一 StorageCoordinator 串行临界区和缓存不变量保持成立。
10. v1.0–v1.3 数据快照均能无损加载，v2 数据可被 v1.3.0 回读。
11. Service Worker 重启不导致数据丢失、伪成功或错误行情状态。
12. 所有鼠标操作均有键盘等价路径，Dialog 和异步重渲染焦点正确。
13. axe 无 critical/serious 问题，文本对比度和触控目标满足约定。
14. 静态检查、覆盖率、单元、组件和真实扩展 E2E 全部通过。
15. 不新增权限、远端代码或模拟行情。
16. 构建产物确定、完整、在体积门禁内，远端 CI 和 Release 全绿。
17. v2 中不存在 v1 运行时兼容代码，并完成冻结 v1.3.0 包的真实回滚/再升级验收。

## 17. 主要风险与控制

| 风险 | 控制措施 |
|------|----------|
| 一次性重写导致行为遗漏 | 先冻结行为基线和历史数据夹具，再实现新模块 |
| Application 或 AppShell 形成新单体 | 按 Quotes/Portfolio/Preferences/Search 拆用例，AppShell 只组合和路由 |
| Web Components 重渲染丢焦点 | 稳定 DOM、keyed update、焦点与节点身份组件测试 |
| ESM/TypeScript 构建与扩展运行差异 | Playwright 只加载正式 `build/extension/` 产物 |
| TypeScript 提供错误安全感 | RPC 边界继续执行运行时校验 |
| Service Worker 内存被回收 | 用户数据依赖 StorageCoordinator，退避依赖 storage.session，每次激活重建初始化屏障并 ensureAlarm |
| 新架构增加文件与概念数量 | 每层限制职责，使用架构检查和模块文档保持可发现性 |
| 回退时数据不兼容 | 不保留 v1 运行时代码；保持 schema v2，以冻结 v1.3.0 包执行回滚和再升级测试 |
